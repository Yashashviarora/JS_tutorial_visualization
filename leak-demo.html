🧟 The Event-Listener Leak — feel it, then fix it

Both mini-apps below simulate an SPA where clicking "Open Chats" runs openChatView(). The user opens and leaves the view many times. Same user behavior, two different codes. Click "Open Chats ×10" on BOTH sides, then scroll each gray box and compare!

❌ Leaky app (no cleanup)

0
Listeners attached
0
Handler runs on last scroll
0 MB
Memory pinned by closures
⬇ scroll me and watch "handler runs" ⬇
→ click "Open Chats ×10", then scroll the box

✅ Fixed app (cleanup before re-add)

0
Listeners attached
0
Handler runs on last scroll
0 MB
Memory pinned by closures
⬇ scroll me — always smooth ⬇
→ click "Open Chats ×10", then scroll the box
What to observe: after "Open Chats ×10" — the leaky side shows 10 listeners, ~40 MB pinned, and ONE scroll runs the handler 10× (each doing fake work → scroll feels heavy; click ×10 a few more times and it gets worse). The fixed side always shows 1 listener, ~4 MB, and scroll runs it once.

The entire fix is 3 lines — remember the previous listener (in a closure!) and remove it before adding a new one: 
if (currentCleanup) currentCleanup();          // ✂ undo the previous visit first
box.addEventListener("scroll", onScroll);
currentCleanup = () => box.removeEventListener("scroll", onScroll);
⚠ Bonus experiment: open DevTools Console and run getEventListeners(document.getElementById('l-scroll')) — Chrome lists every stacked listener on the leaky box. Try the same for 'f-scroll' → always just one.
